# 发布与安装

文件名沿用旧名，以免已有链接失效。仓库按维护者的决定公开。

## 上传到仓库

可通过 git 推送或网页上传。要求：

1. 仓库根目录直接包含 manifest.json、README.md、src、dist 等；dist 中包含 index.js、index.css 和 index.js.map。
2. 源码、dist 和 manifest 版本必须一致，不能只上传源码。
3. 不上传聊天、settings.json、.env、密钥、node_modules、备份和本机验证记录，也不能只上传一个 ZIP。
4. 提交前检查文件列表。`pnpm release:check` 检查版本是否一致、dist 是否由当前源码构建（逐个比较 dist/index.js.map 中的源码与当前 src 文件，统一换行后比较）、更新说明是否已构建、docs/prompts 是否与源码重新导出的结果一致，以及根目录是否有多余文件、是否有疑似密钥。改了源码要先 `pnpm build`，改了提示词要先 `pnpm export:prompts`；构建和导出方面的问题一次列出。

## 安装和更新

在酒馆扩展面板中点击「安装扩展」，填入仓库地址。插件启动时请酒馆对安装目录执行 git fetch（/api/extensions/version），落后于安装来源时，打开宝书弹出更新窗口；确认后调用酒馆的扩展更新接口（/api/extensions/update，即 git pull），成功后自动刷新页面。更新窗口里的版本号和说明从安装来源的 GitHub 仓库读取 manifest.json 和 README 中「X.Y.Z 的改动」一节，所以每次发布都要在 README 写这一节。也可以在「管理扩展」中更新。manifest 中 auto_update 为 true：打开酒馆的「在扩展更新时通知」后，有新版本时酒馆会提示；酒馆自身升级时按酒馆设置顺带更新本扩展。更新只从本扩展的安装来源拉取；安装来源是原版仓库时插件不提示、不更新，插件自身不访问原版的更新源。手动安装见 README。原版和本版共用同一份数据、宏和事件，不能同时启用。

接续旧聊天前参阅 [旧记忆接续说明](LEGACY-COMPATIBILITY.md)：已知的 V3 格式直接读取，可确定对应关系的 V2 格式在本地转换，无法识别的格式只读保护。升级无需全部重新摘要。

「全部重新摘要」（1.4.2 之前叫「重建本聊天记忆」）保留，但不会自动执行：需手动确认，执行时按楼层顺序请求模型，可能产生费用，并替换已有摘要和模型记录的状态；各页面的手动修改单独保存，完成后保留。取消、失败或刷新页面后可以从停下的楼层继续。使用前先备份。

## 不做的事

不使用上游的一键更新（插件内的更新只拉取本扩展的安装来源），不提供 GitHub Pages、自动 Release 或自动部署。package.json 中的 private: true 仅用于防止误发布到 npm，与仓库是否公开无关。

公开仓库中不放置授权聊天截图、私人联系方式或令牌。
